## 2. R3-01 空缓冲时仍越过实时事件水位：P0

### 精确复现

使用 reorder_window_s=2，标准 RID 观测，位置不变，观测 ID 不同：

| 请求 | processingTime | 观测 measurementTime | 当前行为 |
|---|---:|---:|---|
| a | t=1 | t=1 | 缓冲 |
| empty | t=3 | 空批 | 冲刷 t=1 后，将主状态及水位直接推进到 t=3 |
| b | t=3.2 | t=2.5 | 仅晚到 0.7 秒，进入缓冲 |
| flush | t=5 | 空批 | t=2.5 出缓冲，被 stale_obs_ignored，lastObservedAt 仍为 t=1，rejected 为空 |

输入延迟 0.7 秒小于约定的 2 秒，不能因一次空批冲刷而失去更新机会。

### 根因与修复要求

`engine.py:_process_locked` 仍有“buffer empty: coast by processing clock is allowed”分支，直接调用 `_advance_lifecycle(pt, mutate_filter=True)` 并把 event_watermark 设为 pt。当前缓冲为空只说明当前没有待处理项，不代表以后不会到达仍在容忍窗内的观测。

1. realtime 提交水位以 processingTime−reorder_window 等明确事件水位机制推进；是否有缓冲不能改变时间容忍语义。replay 单独按虚拟时钟规则推进。
2. 接纳本批合法候选、合并缓冲、排序、冲刷时保证整体事件时间顺序。不能先推进状态再接受更早但合法的新候选。
3. 主状态及生命周期沿提交水位推进；展示可向处理时刻预测，但必须在副本上，时间字段准确且有预测上限。
4. 除明确窗口外拒绝，不得把合法窗口内观测当 stale 后仍记成功。不得通过取消空批、关闭 reorder 或换成 replay 绕过。
5. 同一缺口补充“空批后延迟观测”“带新观测的请求恰好清空缓冲后再来延迟观测”“不同设备频率”的测试。原 2502 段和不规则节奏测试继续通过。

## 3. R3-02 同时刻主来源选择仍依赖数组顺序：P0

### 精确复现

同 SN、同一时刻、同一批请求：RID 位于经度 117.2，频谱位置偏移 0.0002 度，其余相同。

| 输入顺序 | 输出 positionSource | 输出经度 |
|---|---|---:|
| RID → 频谱 | rid | 117.20000000000002 |
| 频谱 → RID | rid | 117.20004848484848 |

两者来源和时刻相同，只变更观测数组顺序，融合位置就不同，第二种顺序仍混入了先创建频谱状态的影响。

### 根因与修复要求

`_ingest_microbatches` 中 identity 列表保留原数组顺序，逐条建轨／更新。频谱先到同批时先初始化主状态，再执行 RID 更新，与先按 RID 初始化不同。

1. 同一事件时间内先完成身份／目标分组，再按明确、稳定、配置化的优先规则选择一个主位置观测；再初始化或更新主状态。有效及时 RID 优先的本轮约定保持不变。
2. 其他来源只维护来源轨迹、身份、质量及后备作用，不能在主来源之前无意改变初始滤波状态。
3. 补 RID／频谱／雷达同时刻排列置换测试，验证目标归属、主来源和位置等价；fusionId 随新建顺序不同可归一后比较，不能据此跳过位置检查。
4. 对同事件时刻分属不同 batch 的情形，明确 API 是以请求批作为完整微批，还是允许缓冲汇聚；不要承诺未实现的跨批完全顺序不变性。实时缓冲中同一时刻的各来源应按已定义规则统一处理。
5. 不改变“来源优选＋KF”为未经标定的多源平均，不改测试坐标或加样例专用分支。
