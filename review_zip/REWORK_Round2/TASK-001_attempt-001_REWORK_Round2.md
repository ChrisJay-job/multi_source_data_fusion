## 2. 连续回放的独立审计：本轮不能通过的主要原因

使用包内原始连续段，以逐观测 `_apply_update` 调用和实际 hits 增量计数，不复制真实 SN／坐标到审计结果。最后额外发空批冲刷缓冲。

| 指标 | realtime 独立结果 |
|---|---:|
| 输入观测 | 2502 |
| 唯一 observationId | 2502 |
| 调用位置更新入口 | 2502 |
| 实际位置更新 | 513 |
| stale_obs_ignored | 1989 |
| 显式拒绝 | 0 |
| 最后冲刷前／后待处理数 | 6／0 |

1989 条约占 79.5%。输入时间非递减，并非外部乱序；服务内部先预测到未来，再把随后出缓冲的正常观测当成旧数据丢弃。将所有已调用入口的 ID 写入 seen_obs 又使其无法正常重试。

提交方 `updated=417` 是“after_hits 比 before_hits 大的请求数”，不是实际更新的观测数；`buffered=803` 是某类请求计数，不是待处理观测数；`processed=1699` 还根据 watermark／lastObservedAt 推测，不能证明 1699 条观测被应用。拒绝数为 0 不能支持“无丢点”。

证据：`continuous_audit_results.json`、`audit_continuous.py`。另附 replay 对照审计输出。

## 3. 必修项

### R2-01 实时状态／水位只修了规则间隔：P0

位置：`engine.py:_process_locked` 的 `not ready and not ready2` 分支、`_advance_lifecycle`、`_snapshots`。

`allow_predict_display=True` 形参未参与判断；缓冲未成熟时仍用 processingTime 推进主 KF 和 stateTime。完美 1Hz 测试能通过，但不规则节奏会再次忽略正常观测。

整改：

1. 维护单调的提交事件水位，表示已完成的事件时间边界；实时水位不能大于尚未成熟数据所在的已提交边界。首次只有缓冲时，不以 processingTime 假装已完成处理。
2. 主滤波状态只沿提交事件时间推进。展示预测从副本生成，不能写回可更新主状态。
3. 生命周期、来源时效和最后有效观测时间使用一致时钟；快照预测坐标对应时刻必须与 stateTime 或显式 displayStateTime 一致。
4. 预测时长到期停止移动；空批也按事件水位推进，不能借“没有成熟点”跳到 processingTime，破坏缓冲。
5. 窗口外旧数据显式拒绝；窗口内合法、按序数据不能静默 stale。不要通过设 reorder_window_s=0 或全部切 replay 绕过。

附带不规则输入时刻 `[1,3,3.2,3.4,3.6,4,5,6]` 已能复现，不依赖真实数据。

### R2-02 非主来源仍会把状态重复预测：P0

位置：`_apply_update` 在主来源选择前无条件 predict(dt)，非主来源分支没有推进 stateTime，随后生命周期再次按原 stateTime 预测。

复现：在 t=1 设置可控速度 10m/s，t=2 收到绑定雷达且 RID 仍有效。物理上应推进 1 秒，实际主状态被推进两次。

整改：来源选择、门控和预测先在候选副本计算，真正提交时确保每个 dt 只使用一次。可以让非主来源不动主 KF，也可以在明确事件推进中同步更新 KF 与 stateTime；不能出现坐标已经前推、时间仍留原处。跳点拒绝路径也不能先动 KF 后返回而保留旧时间。

### R2-03 全局分配被回退路径绕过：P0

位置：`_global_assign_radar` 对虚拟未匹配列执行 `_ingest(obs)`，随后进入 `_gated_pick`，后者不使用同样的创新门控和矩阵占用约束。

复现：一个 RID 目标与约 86 米外的雷达观测，创新距离已超过代码设置的 6.0，LSA 本应未匹配，回退后仍绑定到 RID。

整改：

- LSA 未匹配应直接进入独立新建／受控候选路径，不能再次执行更宽松最近邻；矩阵排除的边不得通过回退被选回。
- 预测位置和创新协方差应对应同一观测时刻；当前 `_mahalanobis` 使用旧位置及旧协方差，和预测位置距离不同步。使用完整创新矩阵并明确平方距离／距离门限单位。
- 同设备同轮已分配实体必须被占用；不同设备可关联同一实体。
- 歧义分支目前 `continue` 后没有建临时实体、缓存待判或明确拒绝，却把观测记为 seen。修成有输出／可追溯的确定处理路径，不能悄悄丢失。
- 增加真实竞争候选的非贪心测试及顺序置换测试。仅在两个远隔目标上核对“数量为 2”不能证明全局分配正确。

### R2-04 去重未覆盖当批／缓冲，冲突未原子拒绝：P0

位置：`_process_locked` 在 accepted 构造时只查已提交 seen_obs。

复现：同一请求内同观测两次更新 2 次；观测尚在缓冲时换 batch 重发，冲刷后仍更新 2 次。已有 observationId 内容变化只进入逐条 rejected，error 为 None，同行合法新观测仍改变状态。

整改：

- 统一检查本批、缓冲中和已提交三个阶段的观测身份；完全相同只处理一次。
- 同 ID 不同内容按原契约整批 409，发生在任何阶段都不改变轨迹、缓冲、序号、幂等和事件。
- 已接收／待处理／已更新／已拒绝状态区分清楚；不能将静默忽略当作已成功处理。
- 保留现有 session 锁及异常快照回滚，补异常后同 batch 再试证据。

### R2-05 TTL 和缓存容量仍未闭环：P1，本轮必修

`session_ttl_s` 的执行分支仍是 pass；SessionStore 没有 session 淘汰；seen_obs、来源绑定、拒绝身份对没有 TTL／容量。_store_cache 会直接移除过期或超容量响应，旧 batch 再来时可按新批执行。

复现：max_cache=1，同一处理时刻先发 a 空批、再发 b 空批、再重试 a，返回新的 seq=3，未拒绝也不是原响应 seq=1。

整改：明确定义有界重试窗口和容量策略并执行。窗口内保持原响应或返回明确容量／已过期错误；不能静默重新执行。过期批次识别与响应缓存分别设计，元数据也应有界；可采用会话生命周期／窗口协议或受限接收策略，无需引入新基础设施。会话关闭或淘汰必须明确新 epoch 及调用方行为。配置存在不等于已经实现。

### R2-06 输出和映射保留缺口：P1，本轮必修

- Track 内有 altitudeDatum，TargetSnapshot 没有该字段，标准输入 relative_takeoff 输出只剩高度数值。
- `_active_sources` 条件为 confirmed OR hits>=1，所有一击来源都会成为有效来源，confirm_hits 没有真正限制确认状态。
- assumed RID 身份仍被当作可信 SN，field_mapping 配置仍未参与执行；历史时间全部默认 UTC，虽然增加了标记，但仍缺可配置源时区。
- 标准 speed 未检查有限数，非法 verticalSpeed 类型可能从 Observation 构造直接抛出，绕过逐条拒绝和过程异常信封。

整改：补高度基准及来源绑定确认状态输出；有效 sources 与候选来源分开。历史字段假设通过显式配置控制，保留未知状态；模拟测试使用明确可信的合成标准输入，不把原始列名猜测当确认依据。所有非有限值／类型错误走明确拒绝或字段降级规则，标准 processingTime 也要求带时区。先保持水平融合，不猜 -2 或新增垂直算法。
