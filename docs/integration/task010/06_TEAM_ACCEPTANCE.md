## 责任分工

- 算法方：版本与指纹、核心/API/适配器部署说明、规范输入校验、算法输出、关联/拒绝解释、现场调参依据。
- 后端：设备接入/清洗/时间统一、稳定ID、持久原始数据、会话归属/结束、QoS1消费去重落库、结果转发前端、恢复/重发和鉴权。
- 前端：后端业务topic消费、点/段幂等归并、原始与融合与预测分层、轨迹和点详情、未知海拔/缺口/冲突明示、可控渲染/分页、重开从后端恢复历史。
- 运维：网络/NTP/镜像/磁盘、Broker账户和ACL、TLS证书、资源监控与隔离环境。不要把Docker能启动等同三方业务已通。

## 快速排障

| 症状 | 优先检查 |
|---|---|
| HTTP200但没有线 | 是否3D profile；重排窗/tick/flush；trajectoryUpdates为空还是只是tracks有预测；目标是否只有1点；海拔未知被跳过 |
| 同SN没有合并 | 是否同session；坐标/时间一致性；SN真假；门外/航向/歧义事件；不能直接放宽门来掩盖数据源问题 |
| MQTT只有PUBACK没有结果 | 是否订阅正确tenant/site/result；stored与processed；适配器是否连到正确HTTP核心；inbox/outbox/死信 |
| 1883连不上 | 容器localhost误用、Broker监听/ACL/防火墙、用户名、clientId互踢、TLS-only协议不匹配 |
| 大量late_after_frontier | NTP、created_at语义、延迟/乱序、批大小/队列增长、历史文件是否正确rebase；不能只改时间掩盖延迟 |
| frontend重复线/点 | 是否按pointId/updateId去重；是否把快照预测当历史；QoS1重复消费；跨segment硬连 |
| 后端不知融合原始SN | 是否按提交的observationIds查原始库/evidence；SN与observationId是否混淆；雷达是否本来就无可信SN |
| 核心重启后乱线 | epoch变化、状态丢失；是否在新代际继续拼旧点；适配器暂停/恢复流程 |
| UI卡顿 | 是否每批全量历史重绘/整表DOM；是否主线程解析巨型消息；采用增量、合批、分页和可见图层；后端也记录积压 |
| 结束仍少最后一段 | 是否真正flush/drained，后端是否收到末尾result，源点是否被拒绝，是否仅保留快照80点 |

## 当次会议必须共同确认的结论

“本版本已能做经纬度+海拔实时融合及逐点来源追踪；公司后端落库后向前端MQTT发送绘图增量。飞行结束做尾部排空/分段归档；专门的跨长断点补齐接口尚未实现。先以公司隔离环境验证真实Broker、字段/时钟/坐标与实际速率，再进入现场精度和生产稳定性验收。”
